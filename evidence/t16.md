## 代码侧结论

1. **回归根因**：`scripts/install.ps1` / `setup-hermes.ps1` / `setup-hermes.sh` / `scripts/install.sh`
   的 bootstrap 先做 `uv python find --system --no-managed-python --no-python-downloads --no-project`
   兼容性探测，失败才回落 `--managed-python`，两者都失败才 `python install`。
   编码旧单次调用的 fixture 因此失效。
2. **实测 flag 有效**（宿主只有 Python 3.11，pin 是 3.14）：

   ```
   uv python find --system --no-managed-python --no-python-downloads --no-project cpython-3.14-windows-x86_64-none
   error: No interpreter found for cpython-3.14-windows-x86_64-none in search path or registry   (rc=2)
   uv python find --system --no-managed-python --no-python-downloads --no-project cpython-3.11-windows-x86_64-none
   C:\Users\11429\AppData\Local\Programs\Python\Python311\python.exe                             (rc=0)
   ```

   探测不是摆设：兼容则命中宿主，不兼容则明确失败并回落。
3. **保留中间那次 `--managed-python --no-python-downloads` 探测**：
   删掉它，已装 managed Python 的机器会白跑一次 `uv python install`，违背「重复执行不重复安装」。
4. **顺带修掉两处真实缺陷（fail-closed）**：uv pin 非数字时（测试里写作 `fixture` / `fixture-pin`）
   原实现把 `[version]"fixture"` / awk 字符串当版本比较，前者抛异常、后者判定为兼容并跳过受管安装。
   现 `setup-hermes.ps1` 用 `[version]` try/catch，`setup-hermes.sh` 与 `scripts/install.sh` 的 awk
   先校验两侧 `^[0-9]+(\.[0-9]+)+$`，非数字一律不复用本机 uv；同时修掉
   `"$local_uv" --version` 在 `local_uv` 为空时把 `--version` 当命令执行的问题。
5. **MCP stdio 的 uv 不回退本机**：`pm/install.py::uv_launcher` 撤掉 `find_local` 分支，
   与 `tools/mcp_tool_config.py:275` 的文档口径一致（「Never the user's copy」）。
   新增 `tests/pm/test_uv_launcher_contract.py` 双向锁定：

   ```
   === Summary: 1 files, 2 tests passed, 0 failed (100% complete) in 1.6s (1 worker) ===
   ```

## 未验证边界

- **真实下载完成**：本机对 `files.pythonhosted.org` 与 release URL 无 egress
  （`tls handshake eof` / `WinError 10061`），只证明了「决策走受管路径 + 发起下载」，
  未证明落地字节。该分支由既有 PM 测试（faketool 装到临时 store）覆盖。
- **Linux / macOS 通道**：`tests/pm/test_setup_lock_format.py` 带
  `pytestmark = platforms("posix")`，本机 skip；`scripts/tests/*.sh` 同理。
  两处 fixture 已按新调用串更新（`test_setup_lock_format.py`），但**未在 posix 宿主实跑**。
- **PowerShell 7 lane**：本机无 `pwsh`，`-pwsh` 参数全红属环境项。
- **密封发行包 / 跨目标 staging**：`find_local` 在 `manifest.json` 存在或 `target != current_target()`
  时拒绝复用，仅由 `tests/pm/test_local_tools.py::test_sealed_and_cross_target_lookup_never_reuse_host`
  以 fixture 证明，未做真实密封包验证。
- **干净机器全量安装**：`install.ps1` 全流程（含 Git LFS、桌面端构建）未跑。

## 结论在什么情况下失效

- 宿主 uv 版本 ≥ pin 但行为不兼容（例如 uv 改了 `python find --system` 语义），
  ①④ 仍成立，② 的「回退」判定要重跑。
- 若 `pm/lock.json` 的 python pin 大/小版本改变（如 3.15），本机的 3.14.2 将不再兼容，
  探针①的 python 行会变成 `not installed` —— 这是预期，不是回归。
- 账号 store（`%LOCALAPPDATA%\hermes\tools` 一类）如被写入，说明探针未隔离，本证据作废。

| `tests/pm/test_plugin_survival_contract.py` | 1 | 是（原 sweep 同为 `12✓ 1✗`，未进账目） | 二级 profile 不可读时的 skip 文案不含期望路径 |

后两类的定性要靠单文件复跑区分「并发/缓存抖动」与「真实环境缺口」：`test_pip_check.py`
与 `test_plugin_survival_contract.py` 各跑一次，结果记在下面第 5.1 节。

### 5.1 两个可疑文件的单文件复跑

```
scripts/run_tests.sh tests/pm/test_pip_check.py -q
=== Summary: 1 files, 12 tests passed, 4 failed; FAILED: 1 of 1 file in 132.4s ===
scripts/run_tests.sh tests/pm/test_plugin_survival_contract.py -q
    424.83s  tests\pm\test_plugin_survival_contract.py  (420s exceeded; process tree SIGKILL'd)
    progress before the kill: .........F.
```

两条都**与并发无关**（单文件复跑同样复现），定性如下。

**`test_plugin_survival_contract.py::test_update_sync_survives_unreadable_secondary_profile`**
是真缺陷，原 sweep 里它就红过（`evidence/t16-scoped.log:285`），当时既没修也没记进残余表——本轮
补进账目并修掉。原断言：

```python
assert str(broken.parent) in json.dumps(_latest_receipt(home).get("warnings"))
```

`json.dumps` 把 Windows 分隔符转义成 `\\`，needle 却是未转义的原始路径，所以这句只在 POSIX 可能
成立；Windows 上永远不匹配（日志里 needle 与文案指的其实是同一个目录）。修法是在**解码后**的
文案上比：

```python
warnings = _latest_receipt(home).get("warnings") or []
assert any(str(broken.parent) in str(item.get("message", item)) for item in warnings)
```

复跑取证：`scripts/run_tests.sh tests/pm/test_plugin_survival_contract.py -q -k \
test_update_sync_survives_unreadable_secondary_profile` → `1 tests passed, 0 failed (3.5s)`。
顺带一条主机事实：该文件 13 个用例在本机要 >420s，`HERMES_TEST_FILE_TIMEOUT=420` 的单文件跑法会被
SIGKILL，只有整批 `-j 2` 跑法（620.9s）能跑完全部。

**`test_pip_check.py` 的 4 个**（`test_requirements_builds_from_an_overridden_lock_apply_its_overrides`、
`test_streamed_check_still_sees_failures_ahead_of_a_long_expected_report`、
`test_build_accepts_the_override_and_check_still_rejects_what_it_does_not_cover[plain/forced-color]`）
本轮**不修**，把已知与待查写清楚，不含糊过去：

- 原 sweep 是 `✓ tests\pm\test_pip_check.py (16✓, 201.2s)`（`evidence/t16-scoped.log:251`），
  今天 `12✓ 4✗`，属相对 sweep 新增；
- `pm/` 自 tag 起一行没改（`git diff --name-only v0.22.5-fork.1..HEAD -- pm/` 为空）；本轮对
  `tests/pm/_fixtures.py` 只改了 `_run` 的显式 `encoding="utf-8", errors="replace"`，不在下载链路上；
- 失败链：`tests/pm/conftest.py` 把 store/cache 全隔离到 `tmp_path`，所以账号 store 里 11-05 已下好的
  `uv-0.13.5-win32-x64/uv.exe`（31,899,952 字节，仍在盘上）用不上；本机 uv 是 0.13.1，低于 pin；
  PM 去取受管 uv——先 GitHub（`WinError 10061` / `10060`），再回落 R2 镜像，被仓库自己的测试围栏拦下：
  `tests\conftest.py:1432: gaierror → [Errno 11001] test fence: 'hermes-assets.nousresearch.com'
  is a live Nous service; stub the HTTP layer (tests/hermes_cli/anon_portal.py) or mark the test live`；
  同一条 traceback 上方还有本仓假源的 `_RangeError("range probe returned the wrong byte count")` /
  `unexpected download probe status`，说明**本地假源先没命中**才走到真源。
- 结论：这是本机 PM 假源对受管 uv 的供给状态问题，下一步要查的是那条 range probe 为什么返回错
  字节数（假源里 uv 工件是否齐），它不属于 T-01…T-18 任何判据，也不是本 fork 改出来的；与
  `## 未验证边界` 第一条「真实下载完成」是同一道口子。

### 6. 全量目录跑法：本机不可行，记为边界

计划里的第一条宽口径命令覆盖

实测该范围有 **4029 个测试文件**；`-j 2` 下前 11 分钟只跑到 ~200 个文件（约 5%），
