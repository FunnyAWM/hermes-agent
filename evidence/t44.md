# T-44 · 密封包不带 .pyc，安装文件数再降 32%

日期：2026-11-18

## 依据

payload 实测 27,487 文件，其中 `.pyc` **8,724**（venv 4,638 / 源码快照 2,964 / 受管解释器 stdlib
1,061），占 **32%**。T-41/T-43 之后，文件数本身就是安装时长的第一成本（每个新文件一次创建 +
Defender 实时扫描），所以这 8,724 个文件是最大的一块可去项。

`scripts/bundles/bytecode.py` 本来把 pyc 烘焙进 payload，理由是「密封 payload 不带 `__pycache__`
时首启冷编译停摆」。但运行时早已有对无 marker payload 的支持：
`scripts/build/launcher_wrapper.py:104-116` 在没有 `.hermes-baked-pycache` 时把
`sys.pycache_prefix` 指向 `%LOCALAPPDATA%\hermes\pycache`（POSIX 为 `~/.cache/hermes-pycache`），
即「首启编译一次，之后读用户缓存」。所以成本从「每次启动」变成「一次性」，可以接受。

## 改动

| 文件 | 内容 |
| --- | --- |
| `pm/environment.py` | `Environment.sync` 新增 `compile_bytecode: bool = True`；为 False 时不加 `--compile-bytecode` |
| `pm/operations.py`、`pm/client.py` | `build_environment` 透传该参数（RPC 调用同样生效） |
| `scripts/bundles/native.py` | 密封子集 `compile_bytecode=False`、跳过 `bake_bytecode`、调用新的 `_drop_bytecode(out)` 清掉受管解释器自带的 stdlib pyc；全量 bundle 行为不变 |
| `tests/scripts/test_bundle_native.py` | `test_drop_bytecode_strips_every_cache_under_the_payload` |

预期：payload 文件数 27,487 → **约 18,800**（-32%），体积同步下降。

## 代价与边界

- **首启一次性冷编译**：只编译实际被导入的模块（不是全部 8,724），之后从用户缓存读取。
- Desktop 的 ticket bridge 用 `storePython` 直跑、Windows 上不设 `PYTHONPYCACHEPREFIX`
  （`payload-backend.ts::payloadPycacheEnv`），这条路径可能把少量 pyc 写回安装目录；安装目录在
  `%LOCALAPPDATA%\Programs` 可写，不失败、不影响安装时长。正式的后端进程走 `bin/` launcher，
  该 launcher 会设 prefix。
- 全量 `bundled` 变体（非密封）继续 bake，行为不变。
